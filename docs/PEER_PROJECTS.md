## Решения для Reviewer Lab

1. **Объяснять пользу одним сценарием.** Разработчик ревьюера проверяет правило
   и получает конкретный контрпример с кодом, ответом модели и условиями запуска.
2. **Показывать границу ответственности.** LLM ищет или оценивает вариант кода;
   независимый oracle проверяет поведение; оркестратор ограничивает попытки и
   сохраняет доказательства. Дополнительный LLM-судья не заменяет oracle.
3. **Разделять демонстрацию и измерение.** Сохранённый обход помогает понять
   систему. Для вывода о пользе feedback нужен отдельный эксперимент с равным
   бюджетом, повторениями и заранее выбранными кейсами.
4. **Давать короткое воспроизводимое демо.** Просмотр записи и проверка oracle
   должны работать без аккаунта провайдера. Новые модельные вызовы — отдельное
   явное действие с понятной настройкой и расходом квоты.
5. **Сохранять узкий честный MVP.** Сейчас исследуется заданное подмножество
   Python на конечных доменах. Универсальный аудит GitHub PR, production-деплой,
   RAG и дополнительные агентные роли не следуют из существующих результатов.

Эти приёмы использованы как ориентиры для структуры документации. Код и тексты
чужих проектов не копировались. Наши фактические данные и ограничения собраны
отдельно в [EVIDENCE.md](EVIDENCE.md).
